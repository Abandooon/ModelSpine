拥有 TaskView、InteractionPlan、VisualAssetRef 与用户操作提案，不拥有已接受模型或应用状态提交权。输入按交互用途确定：用户任务/角色、版本化需求与候选、模型与合同、来源/问题/差异/检查结果，以及适用时的 CommandBinding 和视觉资产。需求与候选由平台编排通过公开合同提供，模型引用消费 protocols/model-kernel 合同；implementation 的 CommandBinding 只供应应用业务操作绑定，不是所有视图的前置。

基础产品流程需要在生成代码前让用户理解和完善需求/领域候选，再将明确的用户任务与产品视图供下游应用生成使用，并在维护时审查变更。候选审阅、产品视图设计和可执行业务界面分别记录状态；出现一张视图不代表产品已生成、运行或交付。

## 三类交互的输入、动作和权限

| 用途 | 输入与展示对象 | 用户动作及处理责任 | 权限边界 |
|---|---|---|---|
| 需求与候选审阅 | 原文/需求版本、概念/关系/规则候选及来源、正反实例、问题、诊断和支持范围；可没有已接受模型或应用代码 | 查看和比较解释、答复/拒答、逐项确认或提出修订；答复和修订请求绑定来源、问题或候选版本，由 requirements 与平台编排处理 | 确认仅记录用户确认的内容；不自动通过机器检查、接受模型、启动产品生成或执行业务操作 |
| 模型/代码变更审查 | 明确的基线与候选、差异、影响/检查报告、代码事实、所有权和迁移信息 | 解释后果、提出修改、作出审查决定；既定元模型内的模型修改才使用现有 ChangeProposal，交平台装配 kernel 的接受流程；代码修改交相应文件/构建流程 | 审查决定不是模型提交、代码覆盖或部署；各提交点仍核对身份、版本、权限及所需检查 |
| 生成应用的业务 UI | 用户任务、角色、产品视图、版本化领域/项目模型与业务合同；执行操作时另需 CommandBinding 和对应运行对象版本 | 布局/导航/控件投影作为应用生成输入；已绑定控件产生 CommandRequest，由应用后端执行并返回结果/错误 | 未绑定视图只能设计或预览，不能执行业务命令；后端权威校验权限、前置条件和并发版本，UI 不直接改业务状态 |

三类交互以 mode 和引用目标显式区分，可以复用呈现组件，但不能混用动作、写权限或验收结果。需求答复和领域候选修订不强塞进现有同元模型 ChangeProposal，也不借用业务 CommandBinding。对应动作由当前消费者的公开输入合同约束；本稿不新增跨模式的通用动作类型或运行接口。

## 操作设计与视图内容

- project(task,subject,reports,mode) → TaskView，按上表投影需求/候选、变更或产品视图。subject 表示本次投影对象，不是新增共享值对象；不要求先有已接受模型或 CommandBinding。
- bind(view,command_bindings) → InteractionPlan，仅用于应用业务操作，将控件绑定到类型化输入、结果、错误与并发字段。审阅动作由需求/候选或变更消费者绑定相应目标与版本，不经过此业务绑定步骤。
- interpret(user_action,plan,versions) → 按模式产生答复/确认/候选修订请求、ChangeProposal/审查决定、CommandRequest 或 cancelled；无法匹配目标、动作或版本时返回诊断，不能自行提交。
- explain_change(delta,reports,task) → 带出处的后果解释；推断标为假设，不把不可判定解释为无影响。

InteractionPlan 记录本次交互用途、目标版本及可用动作；审阅计划由平台编排按对应消费者的输入合同装配，不要求 command_bindings。业务计划才包含上述 bind 产生的命令绑定，两者不互换使用。

TaskView 共同内容为 id/version/mode/task_ref/explanations/unresolved/layout，语义内容与布局分离。来源、需求、问题、候选、模型、代码及报告引用按用途携带其身份与版本；没有已接受模型的视图不伪造 model_ref，审阅视图不要求 command_refs。应用业务动作须能追溯对应 CommandBinding 及模型/合同版本；缺失或失效的绑定明确显示为不可执行。具体交换字段由实际消费者和正反验收收敛，本页不扩展严格 v0.1。

携带错误、未决、不支持项或未完成检查的候选仍可进入审阅。可解析部分按模型投影，无法投影的部分保留原文/候选载荷与诊断，不为显示而丢掉失败内容或补成合法模型。用户确认、候选状态、检查结论和产品可执行性分别显示，检查通过不是展示门槛。VisualAssetRef 必含来源/用途/语义声明，视觉相似或文生图不能替代合同符合性。

## 操作与失败

序列化依动作输入类型、单位、精度规范进行，不能把所有控件值当字符串，也不全局固定金额表示。需求/候选修订由对应消费者保存新版本，已接受模型由 kernel 保存，业务状态由应用后端管理。UI 可解释禁用原因但不是授权依据；允许本地编辑草稿不等于已保存或已接受，错误保留输入与诊断，收到对应处理结果后才显示持久状态变化；取消不提交。

需求/问题/候选过时、命令绑定过时、模型或业务版本冲突、缺权限、违反前置条件、检查未知与执行错误分别显示。旧视图答复或修改先核对其目标版本；冲突展示可重新确认的差异，不自动将旧回答套到新问题，也不覆盖用户、模型或应用状态。报告与解释保留其对象版本，候选改变后不能把旧通过结论直接标为当前候选通过。解释不能把检查通过称为用户业务许可。

## 设计验收

- 无应用代码、CommandBinding 或已接受模型时，版本化需求/领域候选仍可展示、比较并提出答复和修订；错误、未决及不支持项可见，不能为进入 UI 先冒充检查通过。
- 相同任务/合同可投影为不同布局，布局改变不修改领域语义；产品视图可供应用生成消费，未绑定业务操作保持不可执行。
- 旧问题/候选上的答复、旧基线上的修改及旧业务绑定上的请求分别返回版本冲突；有效审阅动作到达对应消费者，不转成业务命令，也不自动提交模型。
- 修改后果解释绑定版本，输入/状态/错误与对应处理端一致；恢复假设、外部能力缺口、所有权和迁移冲突可见，未知保持未知。

这些是待实现的设计验收，不是本轮通过记录。基础审阅与业务界面属于产品全流程交付；真人理解/操作研究另行评价，不以研究比较完成作为基础界面建设前置，也不以工程验收宣称论文获支持。
